# 콘텐츠 저장·발행·수정 이력 계약

관련 구현 범위는 [이슈 #11](https://github.com/JengYoung/me/issues/11)이다. 이 문서는 콘텐츠 작성·이관, MDX 처리, 발행·조회·검색·수정 이력 구현에서 함께 적용하는 정본이다.

아티클의 Markdown·MDX 작성과 본문 렌더링에는 [아티클 Markdown·MDX 작성과 컴포넌트 계약](mdx.md)을 함께 적용한다. 기본 Markdown 문법의 자동 연결, 추가 props를 위한 JSX 직접 사용, 아티클 전용 컴포넌트의 범위는 해당 문서에서 관리한다.

로컬 발행 명령과 이미지 재사용을 포함한 발행 절차에는 [로컬 콘텐츠 발행 절차 계약](publishing.md)을 함께 적용한다. 공개 파일 준비·검증과 Git 반영·실제 배포의 역할은 해당 문서에서 관리한다.

포스트·시리즈의 카테고리별 경로, MDX 버전 파일, `0.x.x` 초안과 `1.0.0` 이상 공개, `X.Y.Z` 변경 분류, 본문·이미지 보존과 독자를 위한 이력 원칙을 확정한다. 실제 공개 문서 목록과 아래의 미확정 항목은 별도로 결정한다. 이 계약을 작성했다는 이유로 기존 문서를 이동하거나 공개하지 않는다.

## 0. 포스트와 일기의 기능 경계를 유지한다

- `/posts`는 버전별 발행본·수정 이력을 유지하며, 추후 시리즈 기능으로 확장한다. 기존 `series: { id, order }` 관계와 시리즈 탐색의 확장 가능성을 보존한다.
- `/diary`는 **시리즈 기능과 히스토리 관리를 제공하지 않는다.** UI를 숨기는 방식으로 포스트 모델을 재사용하지 않는다. 일기 타입·로더·생성물·작성 명령에 `series`, `version`, `revisions`, `history`, `reason`을 넣지 않으며, 입력에 있으면 검증 오류로 처리한다. 버전 쿼리·과거 본문 로더·버전 선택 UI도 추가하지 않는다.
- 일기는 `apps/web/docs/diary/{year}/{entryId}.mdx`로 저장한다. **연도 폴더 하나에 여러 일기를 두고, 기록마다 단일 원고를 직접 수정**한다. 연도는 저장용 분류이며 시리즈가 아니다. 로컬 전용 초안은 대신 `{entryId}.local.mdx`를 사용할 수 있으나 같은 ID의 두 파일을 동시에 두지 않는다. 발행 시 같은 원고를 `{entryId}.mdx`로 전환하며 버전 파일·백업 원고·이미지 사본을 생성하지 않는다.
- 일기의 필수 필드는 `title`, `entryDate`다. `entryDate`는 한국 시간의 기록 대상 날짜(`YYYY-MM-DD`)이며 실제 달력 날짜를 검증한다. 네 자리 연도 폴더는 `entryDate`의 연도와 같아야 한다. `summary`·`tags`는 선택 입력이다.
- 일기 ID는 파일명에서 `.mdx` 또는 `.local.mdx`를 제외한 값이며 소문자 영문·숫자·하이픈을 사용한다. 초안·로컬 원고를 포함해 모든 연도에서 고유해야 한다. URL은 `/diary/{entryId}`로 유지하고 연도를 포함하지 않는다. 기록 날짜를 다른 연도로 정정할 때는 파일도 해당 연도 폴더로 옮기되 ID는 유지한다.
- 일기는 `publishedAt`이 없거나 빈 문자열이면 초안이며 시간대가 포함된 발행 시각이 있으면 공개 대상으로 검증한다. `.local.mdx`는 날짜가 있어도 공개하지 않는다. `status` 입력은 거부하고, 별도 공개 목록이나 버전 번호를 추가하지 않는다. 기록 날짜를 실제 발행 시각으로 추정하지 않는다.
- 최초 발행 시각은 이후 본문 수정 때 유지한다. 일기 목록은 `entryDate` 내림차순으로 정렬하고 같은 날의 기록은 ID로 구분한다. 본문 수정으로 새 기록이나 이력이 생기지 않는다. `?version=`은 일기의 선택 기능이 아니며 같은 현재 원고만 표시한다.
- 일기 이미지는 같은 연도 폴더의 `./261015.사진.png`처럼 참조한다. 여러 일기의 파일명이 충돌하지 않도록 ID를 붙이는 방식을 권장하되 이미지 버전 접두어와 과거 자산 보존을 요구하지 않는다. 참조한 파일·대체 텍스트·폴더 경계를 검증하고 공개 일기의 `.local.` 이미지 참조를 거부한다. 전체 docs나 참조하지 않은 자산을 공개하지 않는다.
- 공통 목록·본문 헤더·페이지 틀·MDX 본문 컴포넌트와 필요한 파싱·빌드 유틸리티만 재사용한다. 포스트의 시리즈·버전 모델을 일기의 필수 의존성으로 만들지 않는다.
- 기존 날짜형 `.md` 문서는 별도 이관 요청 전까지 그대로 보존한다. 제목·ID·날짜의 의미·공개 여부를 추정해 자동 전환하지 않는다.
- 아래 1, 3, 4절의 버전·과거 본문·자산 보존과 5절의 버전별 발행·이력 규칙은 **포스트·시리즈**에 적용한다. 일기는 이 절의 단일 원고 계약을 따른다. 공통 URL 안정성·MDX 렌더링·초안 비공개·Git 반영과 배포의 경계는 양쪽에 적용한다.

## 1. 독자가 변경의 맥락을 이해할 수 있어야 한다

이 블로그는 독자가 최신 설명뿐 아니라 그 설명에 이르기까지의 과정을 읽을 수 있게 한다. 독자는 각 발행본에서 당시 어떤 환경을 사용했고, 어떤 문제를 만났으며, 어떻게 해결했고, 이후 무엇이 왜 바뀌었는지 파악할 수 있어야 한다.

- 이전 본문을 실제로 다시 읽을 수 있게 보존한다. 수정 날짜나 Git 커밋 목록만으로 본문 이력을 대신하지 않는다.
- 기술 글에는 문제에 영향을 준 도구·라이브러리·운영 환경과 확인 가능한 버전, 문제·제약, 해결 과정·결과를 기록한다. 관련 없는 환경 정보를 의무적으로 나열하거나 확인하지 않은 값을 추정하지 않는다.
- 후속 발행본은 이전 공개 발행본으로 연결하고 바뀐 내용을 읽을 수 있게 한다. 변경 이유는 해당 발행본의 선택 메타데이터 `reason`으로 제공한다. 최초 발행본에는 이전 발행본이 없음을 구분한다.
- 현재 환경에서 다른 결론에 도달하더라도 당시 기록을 최신 설명으로 덮어쓰지 않는다. 새 발행본에서 달라진 조건과 결론을 설명한다.
- 일기에는 기술 글의 환경·문제·해결 형식을 강제하지 않는다.
- 과거 본문 열람과 작성된 `reason`을 통해 변경 맥락을 제공한다. `reason` 생략은 발행을 막지 않으며, 없는 이유를 자동 생성하지 않는다. 문장별 자동 diff나 GitHub 방문을 독자가 이력을 이해하기 위한 필수 조건으로 만들지 않는다.

## 2. 저장 경로와 URL 식별자

저장소 루트 기준 콘텐츠 경로는 다음과 같다. `web/docs`라고 부를 때도 실제 대상은 `apps/web/docs`다.

```text
apps/web/docs/
├── posts/
│   └── {postId}/
│       ├── 0.0.0.mdx
│       ├── 1.0.0.mdx
│       ├── 0.0.0.이미지1.png
│       ├── 1.0.0.이미지1.png
│       ├── 1.0.1.mdx
│       └── 1.0.1.이미지1.png
├── diary/
│   └── {year}/
│       ├── {entryId}.mdx
│       ├── {anotherEntryId}.mdx
│       └── {entryId}.사진.png
└── series/
    └── {seriesId}/
        └── 0.0.0.mdx
```

위 트리는 형식 예시이며 실제 콘텐츠를 만들지 않는다. `0.0.0` 본문·이미지는 초안이며, `1.0.0`과 `1.0.1`은 공개 발행본·자산의 예다.

| 항목        | 계약                                                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- |
| 카테고리    | `posts`, `diary`, `series`로 구분한다.                                                                                  |
| URL 식별자  | 포스트·시리즈는 카테고리 바로 아래 폴더 이름, 일기는 연도 폴더 안 원고의 파일명이 고정 ID다. 일기의 `.mdx`·`.local.mdx` 확장자는 ID에서 제외한다. |
| 표시 제목   | MDX의 제목은 변경할 수 있다. 표시 제목이 바뀌어도 공개된 ID와 기본 URL은 유지한다.                                      |
| 블로그 주소 | `/posts/{postId}`를 기본 주소로 사용한다. 선택한 과거 발행본은 `/posts/{postId}?version={version}`으로 접근한다.        |
| 일기 주소   | `/diary/{entryId}`를 기본 주소로 사용한다. 연도 폴더는 URL에 포함하지 않으며, 모든 연도에서 별개 기록은 다른 ID를 사용한다. |
| 시리즈 주소 | 후속 화면의 `/series/{seriesId}`와 연결한다. 시리즈는 글을 묶는 별도 개념이며 블로그 본문을 옮겨 담는 폴더가 아니다.    |

- 포스트의 폴더 이름을 라우트 `app/posts/[postId]/page.tsx`의 `params.postId`와 컴포넌트의 `postId`로 전달하고, 글 데이터에는 `id`로 기록한다. 모두 같은 글 식별자를 사용한다.
- 제목 변경, 시리즈 편입·순서 변경을 이유로 글의 ID나 기존 URL을 바꾸지 않는다. 물리적 저장 위치를 변경하는 경우에도 이미 발행한 주소의 연결을 보존한다.
- 글의 시리즈 소속·순서는 글의 메타데이터로 연결한다. 시리즈 MDX는 해당 시리즈의 소개·설명을 보존하며, 소속 글의 본문을 중복 저장하지 않는다.
- URL 식별자의 문자·인코딩 규칙은 이관 전에 정한다. 기존 제목이나 파일명을 임의로 ID로 확정하지 않는다.
- 버전 쿼리가 없는 기본 URL은 항상 최신 공개 발행본을 가리킨다. 과거 발행본은 `?version={version}`으로 선택하며, 버전별 경로나 별도 `/latest` 경로를 만들지 않는다. 일기는 버전 선택 없이 단일 현재 원고를 제공한다. 시리즈 공개 이력 화면은 별도로 확정한다.
- 기본 URL과 과거 버전 URL의 canonical은 모두 사이트의 origin과 기본 글 경로로 만든 같은 절대 URL이다. `version`을 포함한 쿼리와 문단 해시는 canonical에서 제외한다.

## 3. 버전은 독립적으로 읽을 수 있는 MDX 발행본이다

- 신규 버전 파일은 `{version}.mdx` 형식이다. 예시처럼 `0.0.0.mdx`, `1.0.0.mdx`를 사용할 수 있다. 기존 `.md` 문서는 이관 대상을 확인할 때까지 보존한다.
- 버전은 세 정수로 구분한 `X.Y.Z`를 사용한다. 첫 숫자가 `0`인 `0.x.x`는 초안이며, `1.0.0` 이상은 공개 발행본이다. 예를 들어 `0.9.9`는 초안이고 `1.0.0`, `1.0.1`, `2.0.0`은 공개 대상이다. 공개 발행본의 숫자는 아래의 변경 분류에 따라 증가시킨다.
- 최신 공개 발행본은 유효한 공개 버전 중 `X`, `Y`, `Z`를 차례로 숫자 비교한 최댓값이다. `1.10.0`은 `1.9.9`보다 최신이다. 발행 날짜·수정 시각·파일 시스템 순서·문자열 정렬로 최신을 선택하지 않으며, `0.x.x`는 비교 대상에서 제외한다.
- 각 버전은 그 시점의 전체 본문과 메타데이터를 담는다. 이전 파일에 적용해야만 내용을 알 수 있는 차이 조각으로 저장하지 않는다.
- 버전은 파일명에서 얻는다. 현재 메타데이터에 중복된 `version` 필드를 추가하지 않는다.
- `1.0.0` 이상의 버전은 공개용으로 검증하는 시점부터 본문·메타데이터·첨부 자산을 함께 완성해야 한다. 실제 공개 이후에는 해당 버전의 제목·본문·메타데이터·발행 시각·첨부 자산을 덮어쓰거나 같은 버전 번호를 다른 내용에 재사용하지 않는다. 오탈자나 설명 변경도 새 발행본으로 기록한다.
- `0.x.x` 초안은 같은 버전 파일을 편집할 수 있다. 새 수정본도 준비 중에는 `0.x.x`로 작업하고, 공개할 때 새 공개 버전과 그 버전에 필요한 자산을 만든다. `1.0.0` 이상의 미완성 파일을 별도 상태값으로 숨기는 방식은 사용하지 않는다.
- 과거 발행본의 본문·메타데이터·자산은 보존하되 사이트의 공통 스타일과 본문 컴포넌트는 현재 디자인을 따른다. 당시 화면의 픽셀이나 실행 중인 외부 서비스까지 복제한다는 뜻은 아니다.
- 과거 MDX는 최신 프런트엔드에서도 읽을 수 있어야 한다. 본문 컴포넌트 API를 바꾸면 기존 발행본과의 호환성을 확인한다. 과거 글을 고쳐서만 새 렌더러에 맞추는 방식으로 해결하지 않는다.
- 콘텐츠 버전은 앱·패키지의 Changesets 버전과 독립적이다. 문서 버전 추가만으로 `package.json` 버전 변경이나 `release:version` 실행을 요구하지 않는다.

### 3.1. `X.Y.Z`는 독자가 변경을 해석하는 기준이다

| 자리 | 증가 기준                                                                                                                         | 예시                                                                                                         | `1.2.3`에서 변경 |
| ---- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------- |
| `X`  | 라이브러리·관련 환경에 전반적인 변화가 있어 이전 설명과 구분해서 읽어야 한다. 적용 환경이나 문제 해결의 전제가 달라지는 변경이다. | 수동 메모이제이션을 설명하던 글을 React Compiler가 적용된 환경의 자동 메모이제이션을 기준으로 새로 설명한다. | `2.0.0`          |
| `Y`  | 현재 문장에 잘못된 사실·설명이 있어 바로잡는다. 라이브러리·환경 차이로 이전 설명을 별도 구분할 정도의 변화는 없다.                | React 18을 설명한 글에서 리렌더링 조건을 일부 잘못 기술한 내용을 같은 React 18 기준으로 수정한다.            | `1.3.0`          |
| `Z`  | 단순 오탈자나 사실이 틀리지 않은 문장을 수정·추가·삭제한다.                                                                       | 오타 수정, 표현 다듬기, 올바른 보충 설명 추가, 틀리지 않은 중복 문장 삭제.                                   | `1.2.4`          |

- `X`는 라이브러리 버전 번호를 그대로 복사하는 자리가 아니다. 글의 적용 전제가 달라져 독자가 이전 설명과 구분해야 하는지를 판단한다. 의존성 버전이 바뀌었다는 이유만으로 자동 증가시키지 않는다.
- `Y`는 이전 설명의 사실 오류를 바로잡았음을 뜻한다. 당시에는 맞았지만 환경 변화로 더 이상 적용되지 않는 설명을 새 환경에 맞추는 경우에는 `X`로 구분한다.
- 문장을 추가하거나 삭제했다는 편집 형태만으로 분류하지 않는다. 잘못된 설명을 삭제하거나 오류를 바로잡는 문장을 추가하면 `Y`, 틀리지 않은 문장의 추가·삭제는 `Z`다. 새로운 내용이 추가됐다는 이유만으로 `Y`를 올리지 않는다.
- 한 발행본에 여러 종류의 변경이 포함되면 `X > Y > Z` 순으로 가장 큰 변경을 적용한다. `X`를 올리면 `Y`와 `Z`를 `0`으로, `Y`를 올리면 `Z`를 `0`으로 초기화한다. `Z` 변경에서는 `X`와 `Y`를 유지한다.
- 본문·메타데이터·이미지 모두 독자가 읽게 되는 내용의 변화로 판단한다. `reason`을 작성할 때는 실제로 바뀐 내용과 그 이유를 설명할 수 있다. 변경 분류를 위해 `reason`을 필수 입력으로 만들지 않는다.
- `0.x.x`를 비공개 초안으로 취급하는 규칙이 우선한다. 환경 변화에 관한 내용을 작성 중이어도 공개할 준비가 되기 전에는 `X`를 `1` 이상으로 올리지 않는다.

React 예시에서는 React 버전과 React Compiler 적용 여부를 함께 기록한다. 자동 메모이제이션은 React Compiler가 제공하며 수동 `useCallback` 사용의 필요를 줄인다. React 19라는 버전만으로 모든 코드에 자동 최적화가 적용되거나 `useCallback`이 항상 불필요하다고 설명하지 않는다. [React의 useCallback 문서](https://react.dev/reference/react/useCallback), [React Compiler 설치 안내](https://react.dev/learn/react-compiler/installation)

### 3.2. 기존 메타데이터에 선택적인 변경 이유를 더한다

`apps/web/docs/posts/`에서 작성 중인 frontmatter의 필드명과 구조를 기준으로 한다. 기존 글을 임의로 수정하거나 이관하지 않는다.

| 필드          | 의미와 형식                                                                         |
| ------------- | ----------------------------------------------------------------------------------- |
| `title`       | 해당 발행본의 표시 제목 문자열                                                      |
| `summary`     | 글의 요약 문자열. 변경 이유를 저장하는 필드로 재사용하지 않는다.                    |
| `publishedAt` | 시간대를 포함한 발행 시각 문자열. 기존 `2026-10-20T18:19:53+09:00` 형식을 유지한다. |
| `tags`        | 태그 문자열 배열                                                                    |
| `series`      | 소속이 있을 때 `{ id, order }`로 기록하는 시리즈 관계                               |
| `reason`      | 선택적인 변경 이유 문자열(`reason?: string`). 없으면 해당 이유 표시를 생략한다.     |

- `reason`은 각 버전의 frontmatter에 기록한다. 생략은 허용하고, 제공한 값은 문자열인지 검증한다. 별도의 필수 변경 요약·환경·이전 버전 메타데이터를 임의로 추가하지 않는다.
- 문제에 영향을 주는 환경과 해결 과정은 본문에 기록할 수 있으며, `reason`에도 필요한 변경 맥락을 설명할 수 있다. 작성하지 않은 환경·버전·이유를 추정해서 채우지 않는다.
- 기존 초안의 빈 필드나 frontmatter가 없는 일기를 이 계약 작성만으로 자동 보정·공개하지 않는다. 추가 필수 여부와 기존 날짜의 이관 해석은 실제 발행 검증을 구현할 때 구체화한다.

## 4. 이미지는 참조한 당시의 파일을 보존한다

- 콘텐츠 이미지 등 버전에 종속된 첨부 자산은 해당 콘텐츠의 ID 폴더에 `{version}.{assetName}.{extension}` 형식으로 둔다. 예: `0.0.0.이미지1.png`.
- 발행본의 이미지 참조는 특정 파일을 명시해야 한다. 같은 주소의 내용이 계속 바뀌는 `latest.png`나 최신 버전의 이미지로 자동 대체하는 규칙을 사용하지 않는다.
- `0.x.x` 접두어의 자산도 초안이다. 최초 공개 시에는 공개할 자산을 `1.0.0.이미지1.png`처럼 공개 버전의 파일로 준비하고 MDX의 참조를 바꾼다. 공개 발행본이 `0.x.x` 자산을 참조하면 검증 오류로 처리한다.
- 새 발행본에서 이미지를 수정하면 새 버전 접두어를 가진 파일을 추가한다. 예를 들어 `1.0.1.mdx`는 변경된 `1.0.1.이미지1.png`를 참조하며, `1.0.0.mdx`와 `1.0.0.이미지1.png`는 그대로 남는다.
- 변경하지 않은 이미지는 보존된 이전 공개 파일을 그대로 참조한다. 글 버전에 맞추기 위한 복사·이름 변경·참조 교체를 하지 않는다. 예를 들어 `1.0.1.mdx`와 `1.1.0.mdx` 모두 `./1.0.0.이미지1.png`를 참조한다. 이미지 파일명의 버전은 그 자산이 추가되거나 변경된 공개 버전이며 현재 글 버전과 같을 필요가 없다.
- 공개 발행본이 참조하는 자산은 후속 버전에서 사용하지 않더라도 보존한다. 정리 작업은 최신 본문뿐 아니라 공개된 과거 발행본의 참조도 확인한다.
- 렌더링·최적화 과정에서도 버전별 자산을 구분한다. 출력 경로 충돌 때문에 서로 다른 버전의 이미지를 덮어쓰지 않는다.
- 내용 보존이 필요한 이미지는 작성자에게 보관 권한이 있는 파일로 관리한다. 외부 URL을 링크했다는 사실만으로 그 이미지의 과거 내용이 보존된다고 판단하지 않는다.
- 초안 자산은 공개하지 않는다. `docs` 전체를 `public`으로 복사하지 않으며, 공개 발행본에서 참조하는 공개 버전 자산만 공개 산출물에 포함한다. 파일명이 `1.0.0.이미지1.png`여도 공개 본문의 참조 없이 자산만 자동 공개하지 않는다.

## 5. 발행과 독자에게 보여줄 이력

- 공개 여부의 정본은 버전 파일명의 첫 숫자다. 계약에 맞는 경로의 유효한 `0.x.x.mdx`는 초안으로 제외하고, `1.0.0` 이상의 MDX는 공개 대상으로 검증·발행한다. 별도 `status`나 발행 목록으로 이 판정을 중복 관리하지 않는다.
- `0.x.x`에 `publishedAt`이 있거나 Git으로 추적 중이어도 공개하지 않는다. 초안의 본문·메타데이터·자산을 공개 목록·이력·검색·사이트맵·브라우저 산출물에 포함하지 않는다.
- 작성자는 로컬 명령으로 발행을 시작한다. 명령은 대상 초안과 변경 분류를 받아 새 공개 MDX와 실제로 추가·변경한 자산만 준비하고, 기존 이미지 참조를 유지한다. 계약 검증 후 이전·새 버전, 추가 파일·재사용 자산, 검증 결과를 표시한다. 작성자는 결과를 확인해 Git에 반영하고 별도 절차로 배포한다. 자동 커밋·푸시·외부 배포는 발행 명령에 포함하지 않는다.
- 로컬 명령으로 공개 파일을 준비한 시점과 배포가 성공해 독자에게 공개된 시점을 구분한다. 명령의 성공을 배포 완료로 보고하지 않으며, 이를 위해 공개 여부를 판정하는 별도 상태값을 추가하지 않는다.
- 공개 문서 목록이 확정되지 않은 기존 글과 `.local.*` 문서를 자동 공개하거나 자동 이관하지 않는다.
- 글 하나와 그 글의 여러 버전을 구분한다. 목록·검색·글 수는 글 단위로 집계하고 최신 공개 발행본의 정보를 사용한다.
- 글의 최초 발행 시각과 각 수정본의 발행 시각을 구분한다. 블로그 목록은 최초 발행 시각을 기준으로 정렬하므로 수정본 추가만으로 최신 글이 되지 않는다.
- 실제 시각에는 시간대를 포함한다. 일기의 `entryDate`는 한국 시간의 기록 대상 날짜이며 발행 시각과 별개다. 날짜만 있는 기록의 실제 발행 시각을 임의로 만들지 않는다.
- 블로그의 이력 목록은 날짜·시각으로 선택할 수 있어야 한다. 현재 선택한 발행본, 번호 기준 최신 공개 발행본, 작성된 `reason`을 구분하고 이전 공개 발행본으로 연결한다. `reason`이 없어도 해당 공개 버전과 본문을 열람할 수 있다. `0.x.x` 작업 과정은 공개 이력에 넣지 않으며, 최초 공개 버전에 이전 초안의 링크를 제공하지 않는다. 독자에게 버전 번호를 외워 입력하도록 요구하지 않는다.
- 선택한 발행본에서는 그 버전의 제목·메타데이터·본문·이미지를 함께 표시한다. 이전 본문에 최신 제목이나 최신 이미지를 섞지 않는다.
- 기본 URL의 초기 HTML에는 최신 공개 본문과 기본 탐색 링크를 포함한다. 과거 버전 URL에서는 최신 HTML을 먼저 제공한 뒤 선택한 버전만 추가로 불러오며, JavaScript를 사용할 수 없으면 최신 글과 안내를 제공한다.
- 존재하지 않는 글·공개되지 않은 글은 404로 처리한다. 공개된 글에서 잘못되었거나 공개되지 않은 버전을 선택하면 초안 정보를 노출하지 않는 복구 가능한 오류와 최신 글 이동을 제공한다.
- 모든 과거 본문을 초기 HTML·클라이언트 번들·검색 인덱스에 통째로 담지 않는다. 검색은 공개된 최신 블로그·일기의 제목·태그만 대상으로 하며, 초안과 과거 본문은 포함하지 않는다.
- canonical은 버전 쿼리나 문단 해시가 없는 기본 글 주소를 사용한다. 사이트맵에는 공개된 글의 기본 주소만 포함한다.
- 포스트·시리즈는 버전 파일 형식을 사용한다. 공개 수정 이력 UI는 포스트가 대상이다. 일기는 단일 현재 원고만 제공하며 시리즈·공개 이력 UI를 개발하지 않는다. 시리즈 화면과 시리즈 공개 이력 UI는 별도로 범위를 확정한다.
- 시리즈 관계는 글의 최신 공개 발행본을 기준으로 한다. 과거 본문을 선택해도 후속 시리즈 탐색은 현재 공개 구성을 따르며, 글의 여러 수정본을 여러 편으로 집계하지 않는다.

## 7. 구현 시 검증할 계약

- 일기의 단일 원고 생성·직접 수정·발행·미리보기가 동작하고, 시리즈·버전·수정 이력 필드와 버전 파일은 거부한다. 일기 타입·카탈로그·화면에 포스트 이력 모델이 들어오지 않는다.
- 공개 일기만 목록·상세·사이트맵에 포함하고 일기 날짜로 정렬한다. `.local.mdx`와 발행 시각이 없는 초안의 본문·이미지는 공개 산출물에서 제외한다.

아래 버전 관련 검증은 포스트·시리즈에만 적용한다.

다음은 구현 완료 조건이며, 문서 작성만으로 통과한 것으로 보고하지 않는다.

- 새 버전을 추가해도 기존 버전 파일·이미지의 내용과 기존 글 URL이 유지된다.
- 환경 변화는 `X`, 같은 환경의 사실 오류 수정은 `Y`, 오탈자·틀리지 않은 문장 변경은 `Z`로 분류한다. 복합 변경의 우선순위와 하위 숫자 초기화를 확인한다.
- 과거 발행본을 선택하면 해당 제목·메타데이터·본문·이미지가 일치하며, 기록된 문제·환경·`reason`을 읽을 수 있다. `reason`이 없는 발행본도 공개·선택할 수 있고, 제공한 값이 문자열이 아니면 검증 오류로 처리한다.
- `1.9.9`와 `1.10.0`처럼 문자열 순서가 다른 사례에서도 번호로 최신을 선택한다. 발행 시각이나 파일 수정 시각을 바꾸어도 최신 선택 기준은 달라지지 않는다.
- 기본 주소는 최신을, `?version={version}`은 선택한 공개 버전을 가리킨다. 어느 버전을 선택해도 canonical과 사이트맵은 쿼리·해시 없는 기본 URL을 사용한다.
- 본문만 수정하면 이미지 파일 수와 기존 이미지 참조가 유지된다. 새 이미지 추가·변경, 이전 공개 이미지 재사용, 최신 버전에서 더 이상 쓰지 않는 공개 이미지 보존이 모두 동작한다. 공개 본문의 초안 이미지 참조는 거부한다.
- 로컬 발행 명령은 새 공개 파일 준비·계약 검증·결과 표시까지 수행하며, 커밋·푸시·외부 배포를 자동 실행하지 않는다.
- 중복 버전, 누락된 참조 이미지, 깨진 이전 발행본 연결을 검출한다. 번호·발행 상태·필수 메타데이터 검증은 스키마 확정 후 함께 구현한다.
- `0.x.x` 본문·메타데이터·자산은 날짜 필드·Git 추적 여부와 무관하게 직접 주소·목록·공개 이력·검색·사이트맵·브라우저 산출물에 노출되지 않는다.
- 버전 선택·직접 접속·새로고침·뒤로가기·오류 복구와 JavaScript 없는 최신 본문 읽기가 동작한다.
- 수정본 추가로 목록 순서가 바뀌거나 글 수가 늘지 않는다. 시리즈 편입 이후에도 기존 주소와 과거 발행본을 읽을 수 있다.
- 단위·컴포넌트 계약은 Vitest, 실제 앱의 읽기·탐색 흐름은 Playwright E2E로 확인한다.
