# 아티클 Markdown·MDX 작성과 컴포넌트 계약

이 문서는 아티클 본문의 작성 방식과 전용 컴포넌트의 적용 범위를 정의한다. 콘텐츠의 저장 경로·공개 여부·버전·자산 보존은 [콘텐츠 저장·발행·수정 이력 계약](storage.md)을 함께 따른다.

기본 Markdown 문법을 아티클 전용 컴포넌트에 자동 연결하고, 추가 props가 필요하면 등록된 컴포넌트를 JSX로 직접 사용하는 방식을 확정한다. 컴포넌트별 API는 먼저 구현과 사용 예시를 제시하고 사용자가 확인하는 순서로 구체화한다. 이 문서의 작성은 렌더러나 컴포넌트 구현 완료를 뜻하지 않는다.

## 1. 컴포넌트의 공유 범위는 아티클 본문이다

- 포스트와 일기는 목록·본문 헤더·페이지 틀과 아래 MDX 렌더러를 재사용한다. 일기에 포스트의 시리즈·버전 이력 모델을 주입하지 않는다. 본문 컴포넌트는 글 종류나 버전 관리 여부를 요구하지 않는다.
- 일기는 `diary/{year}/{entryId}.mdx` 단일 원고와 같은 연도 폴더의 비버전 이미지를 사용한다. 한 연도 폴더에 여러 독립된 기록을 두며 버전 파일은 만들지 않는다. 아래의 과거 발행본·버전 자산 보존 규칙은 포스트·시리즈에 적용하며, 일기의 공개 판정과 자산 검증은 [저장 계약](storage.md)의 0절을 따른다.

- 아티클 본문은 아티클 전용 컴포넌트로 렌더링한다. 인용·링크·이미지·코드 블록·목록뿐 아니라 제목·문단·강조·표 등 지원하는 본문 요소에 같은 원칙을 적용한다.
- 아티클 전용 컴포넌트는 여러 아티클에서 재사용하며, 프로젝트 전역 공통 컴포넌트와 별도로 관리한다. 특정 글마다 같은 요소를 다시 구현하지 않는다.
- 프로젝트 공통 UI를 내부에서 재사용할 수 있다. 아티클에만 필요한 props·표현·동작은 아티클 전용 계층에서 관리하며, 이를 위해 전역 공통 UI의 계약을 확장하지 않는다.
- Markdown·MDX의 컴포넌트 연결과 본문 스타일은 아티클 렌더링 범위에만 적용한다. Header·Sidebar 등 다른 화면의 링크·이미지·목록에 아티클 표현을 전역 적용하지 않는다.
- 디자인 토큰은 프로젝트의 Figma 정본을 함께 사용한다. 아티클 전용이라는 이유로 별도 토큰 체계나 미등록 시각 값을 만들지 않는다. 상세 정책은 [프로젝트 디자인 토큰 계약](../design-tokens.md)을 따른다.
- 전용 컴포넌트는 요소의 의미와 접근성을 유지한다. 링크·목록·인용·제목 등의 의미를 시각적인 모양만으로 대체하지 않는다.

## 2. 기본 Markdown 문법을 전용 컴포넌트에 연결한다

작성자는 일반적인 본문을 Markdown 문법으로 작성한다. 렌더러는 각 요소를 등록된 아티클 전용 컴포넌트에 연결한다. 기본 문법을 사용했다는 이유로 아티클 디자인 시스템의 적용에서 제외하지 않는다.

| 작성하는 요소  | 작성 문법                         | 연결할 아티클 전용 컴포넌트의 역할              |
| -------------- | --------------------------------- | ----------------------------------------------- |
| 인용           | `> 인용문`                        | 인용문과 그 안의 본문을 표현한다.               |
| 링크           | `[텍스트](주소)`                  | 링크의 표현과 이동 동작을 담당한다.             |
| 이미지         | `![설명](./1.0.0.이미지1.png)`    | 이미지와 대체 텍스트를 표현한다.                |
| 코드 블록      | 백틱 세 개로 둘러싼 코드          | 코드 블록의 표현과 관련 기능을 담당한다.        |
| 인라인 코드    | 백틱 한 개로 둘러싼 코드          | 문장 안의 코드를 표현하며 코드 블록과 구분한다. |
| 목록           | `- 항목`, `1. 항목`               | 순서 유무·항목·중첩 구조를 표현한다.            |
| 제목·문단·강조 | 제목, 일반 문단, 굵게·기울임 문법 | 본문의 계층과 타이포그래피를 표현한다.          |
| Markdown 확장  | 표·체크리스트·취소선 등 GFM 문법  | 확장 요소도 아티클 전용 표현으로 연결한다.      |

MDX는 Markdown 요소의 HTML 이름에 컴포넌트를 연결하는 기능을 제공한다. 실제 연결 방식과 필요한 확장 처리는 렌더러 구현에서 정한다. [MDX의 컴포넌트 연결 문서](https://mdxjs.com/table-of-components/), [MDX 사용 안내](https://mdxjs.com/docs/using-mdx/)

## 3. 추가 props가 필요하면 등록된 컴포넌트를 직접 사용한다

- 기본 문법만으로 충분한 경우에는 Markdown을 사용한다. 추가 설정이 필요하면 MDX에서 등록된 아티클 전용 컴포넌트를 JSX로 직접 호출하고 props를 전달할 수 있다.
- 예를 들어 `![설명](이미지)`는 기본 이미지 표현을 사용하고, PC·모바일별 표시 너비를 지정해야 하는 이미지는 전용 이미지 컴포넌트에 해당 props를 전달하는 방식으로 작성한다.
- Markdown 자동 연결과 JSX 직접 사용은 같은 아티클 컴포넌트 계약을 따른다. 같은 내용과 같은 옵션이면 디자인·접근성·동작이 일치해야 한다. 두 작성 방식에 별개의 이미지·링크·인용 구현을 두지 않는다.
- Markdown에서는 컴포넌트의 기본 동작을 사용하고, JSX에서는 해당 컴포넌트가 공개한 props로 필요한 차이를 표현한다. 개별 글에서 디자인을 임의로 덮어쓰는 방식으로 props를 사용하지 않는다.
- 컴포넌트 이름, props의 이름·타입·단위·기본값·허용 범위는 먼저 구현안을 만들고 사용 예시·반응형 동작과 함께 사용자에게 보여주어 확인받는다. 모든 props의 사전 확정을 구현 착수 조건으로 삼지 않는다. `pc/mo width`는 요구하는 기능의 예이며 특정 속성명이나 임의의 숫자 너비를 확정한 것이 아니다.
- 반응형 props의 PC·모바일 구분은 프로젝트의 `desktop:`·`mobile:` 구간을 따른다. 컴포넌트별로 새로운 화면 너비 경계를 정의하지 않는다.
- 이미지의 경로·버전·공개 여부·보존 규칙은 작성 방식과 무관하게 동일하게 검증한다. JSX의 `src`로 참조한 자산도 공개 여부 판정과 자산 수집에서 빠뜨리지 않는다.

현재 구현안의 공개 API와 MDX 매핑은 [`apps/web/shared/article/index.ts`](../../../apps/web/shared/article/index.ts), 사용 예시는 [`article.stories.tsx`](../../../apps/web/shared/article/ui/article.stories.tsx)에서 확인한다. 전역 `shared/ui`와 분리된 아티클 영역이며, 기존 블로그의 이미지·코드 복사·안내 상자·본문 요소 구성을 참고한다. props는 이 구현과 예시를 보고 사용자 피드백으로 확정한다.

- Next.js의 [`mdx-components.tsx`](../../../apps/web/mdx-components.tsx)가 `articleMdxComponents`를 연결하고 `ArticleProse` 안에 본문 스타일을 한정한다. [`scripts/generate-posts.ts`](../../../apps/web/scripts/generate-posts.ts)는 공개 글의 최신 정적 import와 과거 버전의 지연 로딩 목록을 생성한다. 작성·수정·공개 파일 준비 명령은 [로컬 콘텐츠 발행 절차](publishing.md)를 따른다.
- `pnpm --filter web dev`는 실제 `docs/posts`의 초안을 포함해 `localhost:3000/posts`에서 로컬 미리보기를 제공한다. `content:preview`도 동일한 `dev` 명령이며 별도 개발 화면을 만들지 않는다. 기존 `0.x.x.local.md`를 포함한 초안은 원래 경로·본문·날짜를 보존하며, 개발용 생성물과 빌드 경로를 공개 빌드와 분리한다. 초안은 검색·사이트맵·공개 빌드에 포함하지 않고, 미리보기를 발행으로 취급하지 않는다. 포스트의 비버전 이미지 참조는 초안 미리보기에서만 허용한다. 일기는 공개 원고도 같은 폴더의 비버전 이미지를 사용한다. 일기 미리보기는 같은 개발 서버의 `/diary`에서 제공하며 `.local.mdx`와 발행 시각 없는 초안을 공개 빌드에서 제외한다.
- 포스트 상세 페이지의 빌드·조회·검증 방법은 [`screens/posts/README.md`](../../../apps/web/screens/posts/README.md)에서 확인한다. 현재 MDX 처리기는 frontmatter 제목을 페이지의 유일한 h1으로 사용하며, 본문의 h2 이하 제목에 중복 없는 앵커와 목차를 생성한다. 이 구현을 임의의 MDX 실행 문법 전체에 대한 허용 정책으로 확대하지 않는다.
- 이미지의 기본 Markdown 문법과 `ArticleImage`는 같은 구현을 사용한다. 단독 이미지는 캡션을 담는 `figure`, 문장·링크 안의 이미지는 `span`으로 처리해 문단 안에 `figure`를 중첩하지 않는다.
- 이미지 표시 너비는 현재 구현안의 `pcWidth`·`moWidth`로 지정하고, 원본 치수 `width`·`height`와 구분한다. 자산 경로는 이 프로젝트의 콘텐츠 저장 계약을 따른다.
- 코드 블록과 안내 상자는 기존 작성 이름인 `CodeBlock`·`Callout`도 동일 구현에 연결한다. 복사만 클라이언트에서 처리하고 본문 컴포넌트는 서버에서도 렌더링할 수 있게 유지한다.

### 기존 블로그의 아티클 스타일 유지

- 참고 구현은 기능뿐 아니라 본문 배경·여백·글자 표현, 제목 링크 아이콘, 이미지 캡션, 인용·목록·표, 안내 상자의 배경과 이모지, 코드 테마까지 이식 기준으로 삼는다. 임의로 색상·굵기·테마를 재해석하지 않는다.
- 사용자가 별도로 지정한 인용 표현은 기존 왼쪽 세로선 대신 큰 여는·닫는 따옴표와 얇은 괄호형 테두리를 사용한다. 인용 본문에는 조선일보명조체를 적용하고, 출처는 기존 본문 글꼴로 우측에 표시한다. 일기의 인용 본문은 아래 일기 글꼴을 따른다. Markdown `>`와 `ArticleQuote`에 동일하게 적용하며, 장식 따옴표는 보조기술에서 숨긴다. 조선일보명조체는 인용에 한정하며 전역 디자인 토큰으로 확대하지 않는다.
- 사용자가 지정한 일기 타이포그래피는 목록·제목·본문·인용문에 [고운바탕](https://noonnu.cc/font_page/733)을 사용한다. Regular(400)·Bold(700) 웹폰트를 라이선스와 함께 로컬에서 제공한다. 기본 본문·요약은 Figma의 `body-3` 합성 토큰(14px, 행간 24px, 굵기 400, 자간 0)을 적용하고 제목 계층과 코드의 고정폭 글꼴은 유지한다. 공통 아티클의 `serif` 옵션으로 재사용하며 포스트의 기본 타이포그래피와 전역 UI 글꼴을 변경하지 않는다. 이는 사용자가 요청한 글꼴 예외이며 Figma 정본에 없는 전역 토큰을 추가하는 근거로 확장하지 않는다.
- 색상·여백·반경은 Figma 정본과 대조한 현재 프로젝트의 동일 토큰을 재사용한다. 기존 블로그와 토큰이 같으면 새 토큰이나 별칭을 만들지 않는다. 안내 상자는 상태별 배경색과 일반 본문색을 사용한다.
- 사용자가 요청한 기존 아티클 표현으로 본문 `text-body-2`와 굵기 `300`, 코드의 고정폭 글꼴과 Shiki `dark-plus` 테마를 유지한다. 굵기·코드 글꼴·Shiki 색상은 아티클에 한정한 이식 사항이며, 새 Figma 토큰으로 간주하거나 전역 디자인 정책으로 확대하지 않는다.
- 표의 기본 글자 크기는 모바일·데스크톱 모두 `text-body-3`의 14px을 사용한다. 헤더와 본문 셀에 같은 크기를 적용한다.
- 코드 영역은 사이트 Light/Dark와 관계없이 Dark 모드를 유지한다. Markdown 코드 펜스는 [`shared/article/build.ts`](../../../apps/web/shared/article/build.ts)의 `rehypeArticleCode`로 빌드 시 강조한다. 하이라이터를 UI 공개 API나 클라이언트 번들에 포함하지 않는다.
- 강조 결과의 `pre` 색상과 토큰별 `span`을 보존한다. 복사용 원문은 강조 전에 저장해 들여쓰기·빈 줄·마지막 줄바꿈을 유지한다. 언어 미지정·알 수 없는 언어는 일반 텍스트로 표시한다.
- 빌드를 거치지 않은 직접 `CodeBlock` 사용도 같은 코드 영역·글꼴·복사를 사용하며, 문자열 자체를 브라우저에서 구문 분석하지 않는다. 실제 강조 예시는 Storybook의 `HighlightedCode`에서 확인한다.

## 4. 과거 발행본도 같은 계약으로 읽을 수 있어야 한다

- 과거 발행본의 본문·메타데이터·자산은 보존하고, 아티클 컴포넌트의 디자인은 현재 디자인 시스템을 따른다.
- Markdown 연결이나 등록된 컴포넌트·props를 변경할 때는 기존 공개 MDX와의 호환성을 확인한다. 과거 파일을 수정해야만 새 렌더러에서 읽을 수 있는 상태를 만들지 않는다.
- 기본값이나 props의 의미를 바꿔 과거 글의 내용·구조·동작을 다르게 해석하지 않는다. 필요한 호환 처리는 렌더러와 컴포넌트에서 제공한다.

## 6. 구현 시 검증할 계약

다음은 후속 구현의 완료 조건이며, 문서 작성만으로 통과한 것으로 보고하지 않는다.

- 기본 Markdown의 인용·링크·이미지·코드·목록·제목·문단·강조와 지원하는 GFM 요소가 아티클 전용 컴포넌트로 렌더링된다.
- Markdown 자동 연결과 JSX 직접 사용이 같은 내용·옵션에서 동일한 디자인·접근성·동작을 제공한다.
- 추가 props의 기본값·허용 값·반응형 동작은 확정된 컴포넌트별 API 계약과 일치한다.
- 아티클 스타일과 컴포넌트 연결이 다른 화면의 요소에 영향을 주지 않는다.
- 두 작성 방식에서 같은 버전 자산을 해석하며, 초안 자산을 공개하거나 과거 자산을 최신 것으로 대체하지 않는다.
- 과거 공개 MDX가 본문 수정 없이 렌더링되고, 공통 디자인 변경 후에도 내용·의미·접근성을 유지한다.
- Figma 정본과의 대응, Light/Dark, mobile/desktop과 관련 상호작용 상태를 실제 UI에서 확인한다.
